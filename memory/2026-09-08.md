# 2026-09-08 — why the fleet was dead for three days

## Root cause (verified from the Desk, no SSH needed)
Every OpenClaw hero on the Hub, orchestrator included, answers
`401 Invalid API key.` — that string is OpenCode Go's `AuthError`, relayed by the
gateway. The Hub's primary model is `opencode-go/*` and its `OPENCODE_API_KEY`
(from abra, written into `~/Dev/openclaw/.env` on the iMac at deploy) is dead.
`/healthz` and `GET /v1/models` stay 200 the whole time, so `hub status`,
`gotchi-mode status` ("http /v1 live") and the relay health all looked fine.
`./scripts/openclaw-fleet.mjs doctor --live` is the check that shows it.

Fix (Julius, Touch ID): either rotate the key — `abra set gotchibot OPENCODE_API_KEY`
then `abra run gotchibot -- ./scripts/gotchibot remote-openclaw` — or repoint the Hub
to a provider with a live key:
`GOTCHIBOT_OPENCLAW_MODEL=cloudflare-wai/@cf/zai-org/glm-4.7-flash abra run gotchibot -- ./scripts/gotchibot remote-openclaw`.

## Second fault, same three days: heroes never got their prompts
OpenClaw loads AGENTS/SOUL/IDENTITY/USER from the agent **workspace**, never from
`agentDir`. All heroes shared the repo root, so each booted as owned-954 with a
10 KB role-picking AGENTS.md, and "Skills to load: hub-sop, …" named skills in
`.opencode/skills/`, which OpenClaw does not scan. Now: per-hero workspaces at
`config/openclaw/workspaces/<id>/`, rendered from `config/openclaw/templates/`
(decision tables), skills copied per role, `doctor` fails on dangling refs.
Fleet entries carry `sandbox.mode: off` (heroes need host tmux/docker/claude).

## /switch now actually redirects
The gotchi relay resolved the orchestrator once at start; `/switch` never reached
it. It now resolves the focused hero per request. `.opencode/plugins/gotchi-focus-route.js`
puts the `agent-focus.mjs chat --sub` rule in the system prompt while focus is SUB.

## After the redeploy: 429 on the free model, and a dead local CLI
Redeploy fixed the key; the Hub came back on `opencode/big-pickle` (free Zen, pinned
in sessions/.gotchi-model.env). LINK's main session then answered `429 Rate limit
exceeded` — free tier. The deploy now writes `agents.defaults.model.fallbacks`
(opencode-go/glm-5.2 paid → big-pickle → cloudflare free → openrouter free, by
available keys) so OpenClaw rolls over on auth/rate-limit/timeout instead of dying.
Also: `chatViaOpenClaw` is HTTP-first (a provider error is final; the local
`openclaw` CLI fails config validation and only wasted minutes), `gatewayReachable`
waits 8s (first Tailscale hit measured 7s), `chatViaHttp` allows 240s, and
`focus-classify` no longer escalates a comma-separated QUESTION as a multi-part
task (that reset /switch focus to orch mid-conversation).

## LINK's "every 30 minutes" was never scheduled
No LaunchAgent installed on either Mac, no webhook on :8792, no cron402 job
(and no ingress for it), no cycle log ever written. The plist only existed in
config/launchagents/. The playbook said "wakes every 30 minutes" and both LINK
and the orchestrator repeated it. Now `./scripts/gotchibot trader schedule
status|install|uninstall|run-now` (scripts/trader-schedule.mjs) installs the
launchd job on the host it runs on, rendering the plist with that host's real
node path, and status is the only source of truth for "is my cycle scheduled".
Install it on the iMac (desk API, verify terminal and desktop live there).
